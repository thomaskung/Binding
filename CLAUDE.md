# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Conventions

- **Every feature ships with unit tests AND acceptance (Playwright e2e) tests** — standing instruction from the founder. Unit tests live in `tests/` (extract pure helpers to `src/lib/` to create a testable surface when pages are mostly RSC/redirect logic); e2e specs live in `e2e/`. Run the full e2e suite after UI-affecting changes and fine-tune until green.
- **Strategy docs are versioned**: BUSINESS/DESIGN/VISION/LEGAL_REVIEW carry a `**Version X.Y** · Last updated …` header and a Revision History table at the bottom. When materially editing one, bump the version, update the date, and add a history row. **The Revision History is chronological ASCENDING — oldest row first, newest last. ALWAYS append the new row at the very BOTTOM of the table; never insert it above an existing row.** (After adding, verify the last data row is the one you just added.) MEMORY.md is exempt (inherently chronological).

## Commands

**There is NO local Supabase.** Local Docker/Supabase was retired 2026-08-06 — the backend is hosted Supabase and staging is Vercel. `pnpm dev` runs the Next.js app against the **hosted** project using the keys in `.env.local` (see `.env.example`). Don't reintroduce `supabase start`/`db reset` workflows.

- `pnpm dev` — dev server against hosted Supabase (keys in `.env.local`, see `.env.example`)
- `pnpm lint` / `pnpm typecheck` / `pnpm test` — ESLint, tsc, Vitest units (the fast inner loop; no infra needed)
- `pnpm test -- tests/matching.test.ts` — single test file (units: `matching`, `stub-provider`, `frontier-guardrail`, `signup-intent`)
- `pnpm e2e` — Playwright acceptance suite **against deployed staging** (or a preview, via `E2E_BASE_URL`). Needs the `E2E_*` staging secrets in `.env.local` (`.env.example` lists them); `playwright.config.ts` fails fast with the missing names if any are absent. Every spec creates its own per-run users via the service-role key (`e2e/staging-helpers.ts`) — no seeded logins, no clean-DB assumption.
  **Three CI tiers**, each running a different slice against a different target:
  1. **PR gate** (`.github/workflows/ci.yml`, job `e2e`, required check) — the 7 Modal-free specs (`app-shell`, `signup`, `recruiter-onboarding-wizard`, `training-benefits`, `market-intel-dimensions`, `recruiter-pipeline-dashboard` — joined 2026-08-13 for the Phase 2 dashboard-widgets build, admin-seeded/zero-Modal like the rest, founder explicitly opted to gate on it from the start rather than wait for a nightly proof — and `login-oauth`, also joined 2026-08-13 for Phase 3 OAuth login (DESIGN.md §13h), zero Modal cost), against **the PR's own Vercel preview** (resolved from `github.event.pull_request.head.sha`, never `binding-staging.vercel.app`). Skips (via an in-job `gate` step, not a job-level `if:`) for fork PRs and for PRs touching `supabase/migrations/` — see Gotchas.
  2. **Nightly** (`.github/workflows/e2e-staging.yml`, job `functional`, 3am cron) — `npx playwright test --retries=1 --grep-invert "UAT:"` (not `pnpm e2e -- --retries=1`: pnpm forwards a literal `--` instead of stripping it, so the flag silently wouldn't apply): this is the WHOLE `e2e/` directory minus anything tagged `UAT:` in its test name (i.e. every spec file, not a hand-maintained enumerated list — a per-phase "13 + fileX + fileY" count in this doc had drifted out of sync across several phases before being replaced with this plain statement of the actual selection mechanism; don't reintroduce a hand-counted list here, it will drift again), against `binding-staging.vercel.app`, with `E2E_WARM_MODAL=1`. Any new real-Modal spec still needs its `AI_CALL_BUDGET` (`e2e/staging-helpers.ts`) bump confirmed against a real nightly run before trusting the number, per the existing discipline — that part doesn't change just because the file list is no longer spelled out here.
  3. **Post-merge smoke** (`.github/workflows/deploy-staging.yml`, job `smoke`) — `e2e/smoke.spec.ts` alone (with `E2E_WARM_MODAL=1`) + 11 Modal-free specs (the original 7 plus `agent-mcp`, `referral-loop`, `resume-encryption`, `route-smoke` added 2026-08-17) + 3 zero-cost `--grep` tests (`skill-assessment.spec.ts` "draft never candidate-visible until published", `screening-questions.spec.ts` "candidate_score_bonus v2", `company-research.spec.ts` "zero AI or search calls"), all against `binding-staging.vercel.app` right after every deploy — closes the up-to-24h gap for recent features + adds basic route coverage; full real-AI journeys stay nightly-only.
  Set `E2E_WARM_MODAL=1` to make Playwright's `globalSetup` warm the Modal endpoints before a run; leave it unset for Modal-free runs (needs `MODAL_API_TOKEN`, see `.env.example`).
- `pnpm db:push` — apply pending migrations to hosted Supabase (needs `SUPABASE_DB_URL`). CI does this automatically on merge; run it by hand only to get a migration onto staging ahead of a merge.
- `pnpm seed:staging` — (re)seed the hosted staging dataset (`scripts/seed-staging.ts`, real Modal embeddings)
- `pnpm test-data:generate` — regenerate `test-data/smoke-seed.generated.sql` after editing the JSON in `test-data/`

`test-data/` is **kept** and is still the single source of truth for the seed dataset: `scripts/seed-staging.ts` imports its builders, and `tests/test-data-seed.test.ts` guards the generated artifact. It is no longer auto-loaded anywhere (`[db.seed]` is disabled — there is no `db reset`).

**Writing e2e specs**: they run against a shared, never-reset staging database. Create the data you assert on (unique per-run titles/emails), never assert absolute global counts or "the first card", and mind **Modal AI cost** — publish/reveal/extract/refine are real paid round-trips on staging, so call `countAiCall()` and keep them minimal. `AI_CALL_BUDGET` in `e2e/staging-helpers.ts` is **disk-backed, not an in-memory counter** — see Gotchas for why.

`.github/workflows/cleanup-staging.yml` deletes stale `@staging.local` test users **daily** (4am cron) — bumped from weekly now that the PR gate creates its own users on every push.

## Gotchas

- **Migrations: the `db:reset`-from-zero safety net is GONE with local Supabase — this is the one real regression of that move, so compensate deliberately.** `supabase db push` only applies *pending* migrations forward against the live staging DB; it never proves the stack still builds from scratch, and it will not warn you that a migration edited in place already ran. So: (a) **stop editing applied migrations in place** — add a new forward migration instead (the old "in-place is fine pre-launch" allowance depended on being able to reset); (b) to verify from zero, apply `supabase/migrations/` to a **scratch database** (a throwaway Supabase project, or any empty Postgres via `supabase db push --db-url <scratch>`) before merging anything schema-bearing; (c) unique migration version prefixes still matter — a collision is now much harder to notice.
- ~~Seeded `auth.users` rows need empty-string token columns, not NULL~~ — **obsolete since 2026-08-06**: that trap only applied to hand-written SQL seeds, and `supabase/seed.sql` is gone. Users are now created through the admin API (`admin.auth.admin.createUser`) by `scripts/seed-staging.ts` and the e2e helpers, which sets those columns correctly. Keep it that way — don't hand-insert into `auth.users`.
- New tables need explicit `grant` statements (end of `0002_rls.sql`) — RLS policies alone return 42501.
- **A second, undocumented test-account population exists on staging: `test-gate-*@gmail.com`-style emails, plus opaque non-email identity strings (~1850 accounts observed 2026-08-18)** — found while running the comprehensive-seed-data wipe (`scripts/seed-staging.ts --include-staging-local`). These are NOT `@staging.local` (the only domain `cleanup-staging.yml`/`scripts/cleanup-staging.mjs` and this doc's e2e-user docs know about) and are NOT touched by any wipe/cleanup path in this repo — deliberately, since their origin wasn't confirmed and an unscoped wipe would be an unauthorized destructive action. They inflate `auth.users` (1900+ total observed) enough to break naive single-page `listUsers` lookups (see the next gotcha) and will keep growing unbounded until someone identifies what creates them (candidate: `login-oauth.spec.ts`'s real Google OAuth test flow, or some other real-identity-provider test fixture) and adds a matching cleanup path.
- **`admin.auth.admin.listUsers({ perPage: 1000 })` (a single page, no explicit `page`) silently misses users once total `auth.users` exceeds 1000** — found via the same wipe: `ensureUser`'s "email already exists, reuse it" fallback in `scripts/seed-staging.ts` only checked page 1000-and-under, so an old `@smoke.local` account far enough down the sort order was invisible to it and the script threw instead of reusing the account — confirmed empirically: `listUsers` orders newest-first, and a `@smoke.local` account created 2026-08-04 (old) landed on page 10 of 10 at `perPage: 200` while same-day `@staging.local` accounts filled page 1. Fixed there by paginating through all pages; if you write new code against `listUsers`, don't assume a single `perPage: 1000` call sees everyone — this project's staging project already exceeds that.
- **`skill_assessments.created_by` (migration `0033_skill_assessments.sql`) has no `on delete` clause on its FK to `profiles`, so it defaults to RESTRICT** — deleting a profile/`auth.users` row that ever created a skill assessment fails with GoTrue's generic `"Database error deleting user"` and no indication of the real FK cause. Migration `0036_skill_assessments_created_by_set_null.sql` (its own PR, `fix/skill-assessments-created-by-set-null` — kept out of `feat/comprehensive-seed-data` so that PR's own e2e gate isn't skipped by the migrations-touching rule below) fixes this (`on delete set null`) but **has not yet been applied to hosted staging** — `pnpm db:push` was blocked by the auto-mode classifier when attempted from an agent session (schema changes need a human to run them); a human should run it. Until then, anything wiping test accounts (e.g. `scripts/seed-staging.ts`'s `wipeSeedUsers`) must clear referencing `skill_assessments` rows first via a hard delete (`clearNonCascadingReferences` in `scripts/seed-staging.ts`) — note this is a stopgap that hard-deletes the row, whereas 0036 once applied will instead null `created_by` and keep the row; that's an intentional behavior change to reconcile once 0036 lands, not a bug in either place.
- **A `"use server"` module may only export async functions — a plain constant or `interface`/`type` export there silently invalidates ALL of that module's exports under Next's production build**, not just the offending one ("the module has no exports at all" at every import site). `pnpm lint`/`pnpm typecheck`/`pnpm test` (Vitest) do NOT catch this — none of them apply Next's server-action build transform, only `pnpm build` (and therefore Vercel) does. - **Playwright discards the worker after a test failure and re-imports every spec module**, which resets module-level `let` bindings. One real failure once manufactured ten fake ones this way: seven downstream tests called `signIn(page, "")` off a reset variable and each burned ~90s before failing. Guard any test that depends on another test's module-level state with a `requireFixture`/`test.skip` check as the **first statement of the test body** — above any admin/DB call, or an empty id can reach a destructive query against shared staging. `describe.configure({ mode: "serial" })` was considered and **rejected**: it skips independent tests too, which is worse than the guard.

- **A job skipped via a job-level `if:` never reports a status at all** — GitHub treats it as though the check never ran, which permanently blocks a PR if that job is a required branch-protection check. This is why `ci.yml`'s `e2e` job has no job-level `if:`: an in-job `gate` step sets a `skip` output instead, and every later step conditions on it, so the job always runs and always reports a real conclusion.
- **A migration-bearing PR can't be verified against its own Vercel preview** — the PR's migration hasn't been applied anywhere yet, so the preview would run new code against the wrong (pre-PR) schema. This is NOT "staging's schema is older than the PR" — `deploy-staging.yml` applies migrations before deploying, so staging is always at or ahead of merged code; the only gap is the PR's own *unapplied* migration. `ci.yml`'s `gate` step skips the e2e job for such PRs for exactly this reason (an additive migration would happen to run fine against the preview; a destructive one, e.g. a new `NOT NULL` column, would not — skip both rather than risk false confidence either way).
